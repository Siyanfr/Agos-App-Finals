## What this app stores

| Data | Where it lives | Who can see it |
| --- | --- | --- |
| User profile (email, full name, role) | Cloud Firestore, `users/{uid}` | Only that same signed-in user, enforced by Firestore rules |
| Report (reporter ID, description, location, timestamp, status, optional authority notes) | Cloud Firestore, `reports/{reportId}` | The citizen who filed it can read their own reports; any signed-in authority account can read all reports |
| Report photo | Cloudinary (public asset URL, referenced by `photoUrl` on the report doc) | Anyone with the URL, since Cloudinary asset delivery is public by default under the free tier; the URL itself is only ever shown inside the app to signed-in citizen/authority accounts |

## Secrets

- Values my app needs at run time: `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_UPLOAD_PRESET` (Cloudinary), plus the standard Firebase app config (API key, project ID, etc.) generated by the FlutterFire CLI
- Where they live locally: `.env` (Cloudinary values), which is git-ignored; `.env.example` is committed with placeholder values in the same variable names. The Firebase config lives in `lib/firebase_options.dart`, which is generated, not secret by Firebase's own design, and is committed as normal for a Firebase client app
- Where the deploy workflow gets them: not applicable — this project has no CI/CD workflow; builds are run locally
- Anything my deployed web build carries that a visitor could read, and why that is acceptable: the Firebase config (protected by Firestore security rules, not by hiding the config) and the Cloudinary cloud name + unsigned upload preset name (Cloudinary's own model for client-side uploads; the preset only permits image uploads to one folder path, it isn't a key to the whole account, though it is a known, accepted risk that anyone extracting these values could technically upload arbitrary images through this preset — acceptable for a class demo, not for a real production app)

## What protects the data on the service side

Firestore rules (published):

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    function isSignedIn() {
      return request.auth != null;
    }

    function getRole() {
      return get(/databases/$(database)/documents/users/$(request.auth.uid)).data.role;
    }

    function isAuthority() {
      return isSignedIn() && getRole() == 'authority';
    }

    function isCitizen() {
      return isSignedIn() && getRole() == 'citizen';
    }

    match /users/{userId} {
      allow read: if isSignedIn() && request.auth.uid == userId;
      allow write: if false;
    }

    match /reports/{reportId} {
      allow create: if isCitizen() && request.resource.data.reporterId == request.auth.uid;
      allow read: if isAuthority() ||
                     (isCitizen() && resource.data.reporterId == request.auth.uid);
      allow update: if isAuthority();
      allow delete: if false;
    }
  }
}
```

Tested by logging in as each of the 3 seeded accounts (`citizen1@agos.app`, `citizen2@agos.app`, `authority1@agos.app`) and confirming: a citizen only sees their own reports, only authority accounts can change a report's status, and no account can write to another user's `users` profile document.

Cloudinary has no equivalent rule system for this free-tier setup; the unsigned upload preset is the only access control on the photo storage side, scoped to allow uploads only, not deletion or listing.
