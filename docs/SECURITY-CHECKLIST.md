## Backend and security rules

| # | Check | Yes / No / N/A | Evidence |
| --- | --- | --- | --- |
| 13 | Firestore and Storage rules are not left open to anyone; they require an authenticated user | Yes | Firestore rules require `request.auth != null` via an `isSignedIn()` helper on every `reports` and `users` operation. Published and tested by logging in as `citizen1@agos.app`, `citizen2@agos.app`, and `authority1@agos.app` and confirming role-appropriate access. |
| 14 | Rules restrict a user to their own documents where that makes sense | Yes | A citizen can only `read` a `users/{uid}` doc matching their own auth uid, and can only `read`/`create` `reports` where `reporterId` matches their own uid. Only `authority`-role accounts can read all reports or update a status. |
| 15 | If Supabase: Row Level Security is on for every table | N/A | This project does not use Supabase. |
| 16 | Firebase and Google API keys are restricted in the Google Cloud console to the APIs and app they are for | No (deliberate) | Left unrestricted; access is enforced by Firestore security rules (see rows 13–14), which is the layer that actually protects this app's data. Restricting the key in Cloud Console is good practice for production apps but not something pursued here, an acceptable tradeoff for a class project. |
| 17 | I opened the app signed out and confirmed I could not read or write data I should not | Yes | Logged out and confirmed no screen displays report data without an authenticated session; the app has no route that shows Firestore data pre-login. |
| 18 | Seed and sample data is invented, not real people's data | Yes | The 3 seeded accounts (`citizen1@agos.app`, `citizen2@agos.app`, `authority1@agos.app`) and all test report descriptions/locations used during development are fictional, made up for testing, not copied from real people or classmates. |

## Input and app surface

| # | Check | Yes / No / N/A | Evidence |
| --- | --- | --- | --- |
| 19 | Input is validated before it is written, not only styled as valid in the UI | Partial | The Submit Report screen blocks submission client-side if a photo or location is missing. Firestore rules independently enforce that `reporterId` on a new report must match the signed-in user's own uid, so a client-side bypass can't spoof another user's report. Not yet enforced: a Firestore rule restricting `status` to only `"Pending"`, `"Resolved"`, or `"Rejected"` — currently an authority account could theoretically write an arbitrary string value via a malformed request, though the app's own UI never generates one. |
| 20 | Nothing secret is recoverable from the built app, since a shipped binary can be unpacked | Yes | The values compiled into the app (Firebase config, Cloudinary cloud name and unsigned upload preset) are all designed by their respective providers to be client-visible; actual protection comes from Firestore security rules (for data) and the fact that the Cloudinary preset only permits image uploads, not from keeping any of these values hidden. |
